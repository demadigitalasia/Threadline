# Kontrak Teknis — Threadline

| Informasi | Nilai |
| --- | --- |
| Status | Draft lokal, diturunkan dari spesifikasi yang tersedia dalam dokumen proyek |
| Tujuan | Menjaga satu tempat untuk struktur data, integrasi, dan akses teknis |
| Implementasi lokal | Aplikasi Next.js dan migrasi Supabase tersedia di `threadline/`; kesesuaiannya dengan kontrak dan kriteria penerimaan belum diverifikasi penuh |
| Target framework | Next.js stabil terbaru dengan App Router; baseline sumber resmi yang diverifikasi 17 Oktober 2026 adalah lini 16.4. Nomor patch harus diverifikasi dan dikunci saat proyek dimulai. |

Dokumen ini mencatat kontrak teknis Mode Online. Detail database/Auth/Storage di bawah ini tidak menyatakan bahwa implementasi lokal sudah memenuhi kontrak. Kebutuhan produk, termasuk perilaku Mode Demo, dan keputusan yang disepakati dirangkum di [PRD-Threadline.md](PRD-Threadline.md).

## 1. Arsitektur

- Frontend menggunakan rilis stabil terbaru Next.js dengan App Router, bukan canary. Rujukan resmi yang diperiksa pada 17 Oktober 2026 adalah Next.js 16.4; nomor patch yang digunakan harus diverifikasi kembali lalu dikunci di lockfile saat implementasi.
- Runtime minimum adalah Node.js 20.9. Jika proyek menggunakan TypeScript, gunakan versi 5.1 atau lebih baru.
- App Router memakai Server Components secara default. Gunakan Client Components untuk state/event interaktif, API browser, penyimpanan lokal Mode Demo, dan langganan Supabase Realtime.
- Proyek mengikuti konfigurasi Cache Components yang didukung rilis Next.js stabil yang dikunci. Data akun, job, thread, file, dan data privat lain tidak boleh dimasukkan ke cache bersama lintas pengguna; jangan gunakan `use cache` untuk data tersebut pada MVP. RLS tetap menjadi penjaga akhir akses data.
- Mode Online menggunakan `@supabase/supabase-js` v2 bersama `@supabase/ssr`, dengan klien terpisah untuk browser dan server serta sesi Auth berbasis cookie. API `@supabase/ssr` perlu dipasang pada versi yang kompatibel dan dikunci saat implementasi karena status paketnya masih beta.
- Supabase Auth memakai email dan kata sandi. Pendaftaran terbuka membuat profil Freelance pending/nonaktif; konfirmasi email wajib sebelum masuk antrean review, kemudian Admin/Super Admin menyetujui sebelum fitur operasional terbuka. Pengguna terverifikasi dapat masuk untuk melihat status pendaftaran. Alur pemulihan kata sandi mengirim tautan melalui SMTP produksi, dan logout mengakhiri sesi perangkat. Batasi URL redirect yang diizinkan untuk verifikasi serta reset dan aktifkan perlindungan abuse/rate limit Auth.
- Urutan role adalah Super Admin, Finance, Admin, Freelance. Pendaftaran baru selalu Freelance dan harus diverifikasi serta disetujui. Operator tepercaya menetapkan Super Admin pertama setelah email diverifikasi; setelah itu Super Admin mengubah role/status akses pengguna lain melalui RPC ber-audit. Admin dan Super Admin memiliki kewenangan operasional; Finance mengakses laporan finansial, jadwal, dan pencatatan transfer terbatas melalui RPC ber-audit tanpa hak baca job langsung; Admin tetap melihat rekap fee. Super Admin aktif terakhir dan akun Super Admin yang sedang dipakai tidak dapat diturunkan/dinonaktifkan oleh UI.
- `profiles.is_active=false` menonaktifkan akses Threadline: helper identitas mengembalikan null, RLS/RPC menolak data dan mutasi, dan UI menampilkan keadaan nonaktif. Sesi Supabase Auth masih dapat ada di perangkat; untuk offboarding penuh, operator juga menonaktifkan pengguna Auth dan mencabut sesi refresh. Profil serta riwayat bisnis dipertahankan.
- `proxy.ts` mengikuti pola Next.js 16 dan Supabase SSR untuk memperbarui sesi/cookie. Proxy bukan pengganti otorisasi; RLS melindungi data PostgreSQL dan operasi objek Supabase Storage.
- Mode Online berjalan pada satu deployment Supabase self-hosted di VPS Linux menggunakan Docker Compose resmi. Deployment itu menyediakan PostgreSQL, Auth, Storage, Realtime, dan layanan Supabase terkait; bukan project Supabase Cloud. Aplikasi tetap menggunakan Supabase Storage API, sedangkan Cloudflare R2 menjadi backend objek S3-compatible.
- Storage metadata (termasuk `storage.objects`) dikelola Supabase di PostgreSQL; objek biner berada di bucket R2 privat. Threadline menyimpan referensi bisnis file pada `job_files` dan snapshot hasil pada `job_submissions`/`job_submission_files`. Supabase Storage API menerapkan RLS berdasarkan sesi dan relasi pengguna dengan job.
- Konfigurasi backend R2 berada pada service Storage di VPS, bukan di browser atau Next.js: `STORAGE_BACKEND=s3`, `GLOBAL_S3_BUCKET`, `GLOBAL_S3_ENDPOINT`, `GLOBAL_S3_PROTOCOL=https`, `GLOBAL_S3_FORCE_PATH_STYLE=true`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, dan `REGION`. Gunakan endpoint akun R2, region `auto`, dan kredensial yang dibatasi pada bucket backend.
- Browser mengunggah/mengunduh melalui Supabase Storage API/SDK. Jangan memberikan URL publik atau melewati RLS lewat endpoint R2 langsung. URL bertanda tangan yang diterbitkan Supabase Storage adalah akses sementara dan dapat digunakan pemegang URL sampai kedaluwarsa.
- Gunakan bucket Supabase `job-files` privat dan kebijakan RLS `storage.objects` yang memeriksa bucket, ID job pada path, role, dan kepemilikan/penugasan. Freelance hanya dapat membaca file job yang ditugaskan dan menambah file hasil baru; Admin dan Super Admin dapat mengelola file yang belum terikat submission. Objek pada file terkunci hanya dapat dihapus oleh proses retensi melalui Supabase Storage API.
- Konfigurasikan batas global Supabase Storage `FILE_SIZE_LIMIT` sekurang-kurangnya 1 GiB dan pastikan batas bucket `job-files` tidak lebih rendah. Aturan produk tetap membatasi setiap file ke 1 GiB serta total file aktif dan reservation ke 10 GiB per job.
- Gunakan unggahan resumable TUS untuk file di atas 6 MB dan uji end-to-end dengan backend R2 pada versi bundle yang dipin. Jika TUS gagal dengan error `x-amz-tagging`, dokumentasi Supabase menyarankan `TUS_ALLOW_S3_TAGS=false` pada service Storage; verifikasi kebutuhan ini terhadap versi bundle tersebut.
- VPS pada kontrak ini ditujukan untuk stack Supabase. Lokasi deployment frontend Next.js belum ditentukan dan dapat berada pada host terpisah.
- PostgreSQL 17 menjadi baseline karena merupakan versi default pada bundle Supabase self-hosted resmi saat dokumen ini diperbarui. Pin versi rilis Docker Compose Supabase dan gunakan versi PostgreSQL yang disertakan bundle tersebut; jangan meng-upgrade container database secara terpisah tanpa prosedur upgrade resmi.
- Pemilik deployment bertanggung jawab atas provisioning VPS, hardening OS/network, pembaruan layanan, pemantauan, backup, dan pemulihan. Target pilot: backup PostgreSQL dan perlindungan objek R2 harian, retensi 7 hari, RPO maksimum 24 jam, dan RTO maksimum 8 jam. Salinan objek harus memakai tujuan dan kredensial terpisah dari bucket produksi; penyedia/lokasi dan prosedur restore menjadi gerbang wajib sebelum pilot. Mekanisme pemulihan metadata PostgreSQL dan biner R2 dikelola terpisah.
- Notifikasi produk tampil di dalam aplikasi; browser notification bersifat opsional ketika aplikasi terbuka dan izin tersedia. Tidak ada scheduler untuk pengingat produk atau notifikasi latar belakang/server push. Tautan WhatsApp hanya menyiapkan draft. Tugas pemeliharaan harian pada VPS untuk purge file termasuk dalam lingkup operasi.
- Mode Demo memakai penyimpanan browser hanya dari Client Components dan terpisah dari Mode Online. Aksi reset Demo hanya menghapus data lokal Demo. Mode Online memakai data bersama dan sesi Auth; kode reset Demo tidak pernah memanggil operasi penghapusan Online.
- Perubahan jobs dan chat_threads/chat_messages disiarkan melalui Realtime. Event yang diterima klien harus mengikuti hak akses pada [§3](#3-aturan-akses-yang-dibutuhkan); event job atau thread milik pengguna lain tidak boleh terlihat oleh Freelance.
- Pemeriksaan kapasitas dan presence dilakukan dalam operasi database atomik yang dipanggil melalui Supabase; penugasan langsung yang melewati pemeriksaan tersebut ditolak.

Rujukan versi dan integrasi: [rilis Next.js 16.4](https://nextjs.org/blog/next-16-4), [panduan upgrade Next.js 16](https://nextjs.org/docs/app/guides/upgrading/version-16), [panduan Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [self-hosting Supabase dengan Docker](https://supabase.com/docs/guides/self-hosting/docker), [panduan SMTP Auth](https://supabase.com/docs/guides/auth/auth-smtp), [checklist produksi Auth](https://supabase.com/docs/guides/deployment/going-into-prod), [konfigurasi S3 Storage self-hosted Supabase](https://supabase.com/docs/guides/self-hosting/self-hosted-s3), [kontrol akses Storage Supabase](https://supabase.com/docs/guides/storage/security/access-control), [S3-compatible API R2](https://developers.cloudflare.com/r2/api/s3/), dan [batas R2](https://developers.cloudflare.com/r2/platform/limits/). Ringkasan riset ada di [CLOUDFLARE-R2-RESEARCH.md](CLOUDFLARE-R2-RESEARCH.md).

## 3. Aturan akses yang dibutuhkan

| Data | Super Admin | Finance | Admin | Freelance |
| --- | --- | --- | --- | --- |

| job_files dan submission | Mengelola file yang belum terikat submission serta meninjau submission; file terikat tetap terkunci. | Tidak dapat membaca file atau submission. | Sama dengan kewenangan file/submission Super Admin. | Membaca file job sendiri, menambah file, dan membuat submission; tidak mengubah/menghapus file atau relasi submission. |
| job_events | Membaca semua riwayat dan menambahkan event melalui operasi berwenang. | Tidak dapat membaca event job mentah. | Membaca semua riwayat dan menambahkan event melalui operasi berwenang. | Membaca riwayat job sendiri; operasi status/submission menambahkan event identitas sesi. |
| freelancer_payment_* | Mengelola operasi Admin. | Laporan dan histori melalui RPC terbatas; pencatatan/pembatalan via RPC; tidak ada akses SELECT atau mutasi tabel langsung. | Tidak dapat mengakses. | Tidak dapat mengakses. |
| app_settings | Membaca dan mengubah SLA bersama. | Tidak dapat membaca atau mengubah. | Membaca dan mengubah SLA bersama. | Membaca SLA bersama; tidak mengubahnya. |
| chat_threads / chat_messages | Membaca dan membalas di semua thread. | Tidak dapat membaca atau mengirim pesan. | Membaca dan membalas di semua thread. | Membaca dan mengirim pesan hanya di thread sendiri. |
| Supabase Storage `job-files` | Akses sesuai aturan Admin pada semua job. | Tidak dapat mengakses objek. | RLS mengizinkan baca semua job dan unggah file referensi melalui reservation server. | RLS mengizinkan baca file job yang ditugaskan dan mengunggah preview/file asli melalui reservation dengan path, peran, status job, dan ukuran terikat; penghapusan hanya untuk objek unggahan yatim yang belum tercatat sebagai file. |
| Supabase Storage `finance-payment-proofs` | Akses audit melalui signed URL sementara. | Mengunggah bukti; pembacaan Storage hanya diizinkan setelah event pembukaan bukti oleh aktor yang sama, dan bukti tertaut tidak dapat dihapus. | Tidak dapat mengakses objek. | Tidak dapat mengakses objek. |

Kebijakan menegakkan identitas dan role dari profil aktif di sesi/database, bukan mempercayai payload klien. TOTP bersifat opsional; helper `is_super_admin()` memvalidasi sesi, role Super Admin, dan status aktif tanpa mensyaratkan AAL2. Finance tidak membaca tabel job, profil penerima, file, submission, timeline umum, thread, atau pengaturan umum. Finance menerima laporan melalui RPC terbatas; pencatatan/pembatalan, jadwal, serta pembukaan rekening/bukti divalidasi di database dan ditulis ke audit. Role/status akses hanya dapat berubah melalui RPC Super Admin ber-alasan dan ber-audit; audit akun hanya dapat dibaca Super Admin aktif. Pendaftaran publik menggunakan Auth sign-up dengan verifikasi email; email yang belum dikonfirmasi tidak dapat masuk antrean review. Undangan Auth, reset email, resend verification, dan pencabutan sesi dijalankan dari server melalui Auth Admin API; `SUPABASE_SERVICE_ROLE_KEY` tidak boleh tersedia di browser. Bootstrap Super Admin pertama tetap memerlukan `service_role`. Operasi assign dan reassign mensyaratkan freelancer aktif/disetujui, online dengan heartbeat database, status siap, dan kapasitas; status, submission, review, dan pembatalan tetap tervalidasi serta tercatat secara atomik.

AC-01 hanya dapat lulus setelah migrasi yang tersedia di `threadline/supabase/migrations/` ditinjau dan berhasil dijalankan pada instance self-hosted baru dengan versi PostgreSQL dari bundle yang dipin. Pemeriksaan harus mencakup tipe data, nullability, foreign key, unique/check constraints, indeks, aturan cascade/restrict, enum/status yang tervalidasi, serta relasi `jobs.current_submission_id`/`approved_submission_id` ke submission pada job yang sama. Keberadaan file migrasi saja belum membuktikan kriteria lulus. Fee disimpan sebagai bilangan bulat Rupiah dan ditampilkan dengan format `id-ID`.

## 4. Sinkronisasi dan realtime

- Klien memuat daftar job saat masuk dan saat menerima perubahan realtime.
- Job Belum Ditugaskan terlihat oleh Admin dan tidak dihitung dalam kapasitas. Freelance hanya menerima job yang ditugaskan kepadanya.
- Freelance hanya mengirim transisi status yang diizinkan, komentar timeline, unggahan baru, dan submission job miliknya; Admin dan Super Admin mengelola penugasan, review, pembatalan, dan semua job; Finance tidak memuat job langsung dan memakai RPC laporan bulanan serta rincian saldo yang dipaginasi.
- Spesifikasi sumber mencatat debounce sekitar 800 ms sebelum penyimpanan. Perubahan harus menyertakan revision yang dibaca; backend menolak penyimpanan bila revision sudah berubah dan UI meminta pengguna memuat ulang, sesuai D-05.
- Penugasan/pengalihan menggunakan operasi atomik yang memeriksa presence dan kapasitas target. Pengalihan Antre memulai ulang `antre_since`; Dikerjakan/Revisi mempertahankan status dan meminta alasan. MintaACC harus ditinjau sebelum dialihkan; ACC/Dibatalkan terminal.
- MintaACC membuat submission baru dengan minimal satu file dan relasi file yang tidak berubah. File/relasi yang telah diikat terkunci untuk edit/delete biasa. Keputusan Admin menaut ke submission yang sama; pengajuan ulang membuat versi baru. Operasi review tidak boleh menyetujui versi yang bukan submission pending saat ini.
- Admin dapat membatalkan job Belum Ditugaskan, Antre, Dikerjakan, MintaACC, atau Revisi dengan alasan wajib; job ACC/Dibatalkan tidak dapat dibatalkan ulang. Pembatalan menyimpan pelaku dan waktu dalam job serta riwayat. Job Dibatalkan tidak dihitung ke kapasitas atau fee recap. Penghapusan permanen dibatasi pada job Belum Ditugaskan tanpa event, submission, atau file.
- Saat ACC, simpan `approved_fee` dan `approved_for_profile_id` dari assignee saat itu; seluruh fee diatribusikan kepada penerima tersebut walaupun job pernah dialihkan. Jangan mengubah atribusi biasa setelah ACC.
- Deadline menghasilkan penanda Terlambat turunan ketika terlewati kecuali status ACC/Dibatalkan. Urgen dihitung terpisah dari `antre_since` dan nilai SLA bersama.
- Heartbeat memperbarui `last_seen` tiap 30 detik. Presence online berlaku hanya selama umur heartbeat `< 90 detik`; pada `>= 90 detik`, Freelance offline.
- Nilai SLA urgensi dibaca dari satu baris `app_settings`; Admin dan Super Admin dapat memperbaruinya dan seluruh klien Mode Online menggunakan nilai terbaru yang sama, sesuai D-09 dan D-10.
- Batas baca profil mengikuti §3: Admin dan Super Admin dapat melihat direktori/presence untuk penugasan; Finance hanya menerima nama penerima melalui laporan finansial, bukan direktori; Freelance tidak dapat membuat enumerasi profil dan hanya menerima nama yang diperlukan untuk job/thread yang berhak dilihatnya.
- Target tampilan job baru kurang dari 3 detik jika koneksi realtime berfungsi. Jika realtime putus, klien menyediakan pemuatan ulang.

## 5. Storage dan retensi

- Supabase Storage menjadi API aplikasi dan mengelola metadata objek; Cloudflare R2 menjadi backend S3 untuk objek biner. Bucket logis Supabase `job-files` bersifat privat. Bucket fisik R2 khusus backend ditetapkan saat deployment melalui `GLOBAL_S3_BUCKET`. Jangan membuka bucket R2 ke publik atau menggunakan endpoint R2 langsung dari browser.
- Supabase Storage menyimpan metadata objek pada `storage.objects`; Threadline menyimpan referensi bisnis (`id`, `job_id`, `name`, `path`, `file_kind`, `size_bytes`, `uploaded_by_profile_id`, `uploaded_at`, `expired_at`) pada `job_files`. `size_bytes` adalah ukuran terverifikasi. `path` adalah object path Supabase, bukan URL publik. Submission mengikat file melalui `job_submission_files` dan relasinya tetap tercatat setelah biner melewati retensi.
- Kebijakan RLS `storage.objects` memeriksa bucket `job-files`, ID job pada prefix/path, identitas sesi, role, dan relasi assignee. Admin dan Super Admin dapat mengelola file yang belum terikat submission; Freelance hanya membaca job yang ditugaskan dan menambah file hasil baru. File yang terkait submission terkunci terhadap perubahan/penghapusan biasa.
- Backend S3 diatur pada service Storage self-hosted melalui `STORAGE_BACKEND=s3`, `GLOBAL_S3_BUCKET`, `GLOBAL_S3_ENDPOINT`, `GLOBAL_S3_PROTOCOL=https`, `GLOBAL_S3_FORCE_PATH_STYLE=true`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, dan `REGION=auto`. Gunakan token Object Read & Write yang dibatasi pada bucket backend. Rahasia berada di environment server Storage, bukan di frontend.
- Browser memakai Supabase Storage SDK/API untuk unggah, unduh, dan hapus sesuai operasi yang diizinkan RLS. Hindari menghapus baris `storage.objects` langsung dengan SQL: penghapusan objek biner harus melalui Storage API agar objek di R2 ikut terhapus.
- Semua file layak dihapus tepat saat `now >= uploaded_at + 30 hari`, termasuk file pada job ACC. Tugas terjadwal harian di VPS memprosesnya pada eksekusi pertama setelah batas tersebut, menghapus objek melalui Supabase Storage API, lalu menandai `job_files.expired_at`; submission, daftar file, dan riwayat keputusan dipertahankan. Tugas bersifat idempoten dan mencatat kegagalan untuk dicoba ulang. Kredensial berhak istimewa hanya tersedia bagi proses server ini, tidak pada browser.
- Produk menerima PDF, CDR, PNG, dan JPEG; jumlah file tidak dibatasi, ukuran maksimum 1 GiB per file dan 10 GiB untuk biner aktif serta reservation pada satu job. Biner yang sudah dipurge tidak lagi masuk hitungan. Validasi ekstensi, jenis konten, ukuran, dan anggaran total berlangsung di server. Reservation harus dibuat atomik sebelum transfer agar unggahan bersamaan tidak melampaui batas. Jika transfer gagal atau metadata tidak tercatat, reservation dan objek yatim dibersihkan melalui retry.
- Batas produk tetap harus berada di bawah batas bundle Supabase Storage/R2. R2 membatasi satu request atau bagian multipart sampai 4.995 GiB; maksimum objek maupun upload multipart adalah 4.995 TiB dengan maksimum 10.000 bagian. Verifikasi batas end-to-end dengan mode upload dan versi bundle yang dipin.
- Supabase mencatat bahwa resumable upload TUS dengan R2 dapat membutuhkan `TUS_ALLOW_S3_TAGS=false` karena R2 tidak mendukung fitur S3 `x-amz-tagging`; uji konfigurasi terhadap versi bundle yang dipin.

## 6. Kesenjangan perlindungan yang harus diuji

| ID | Kesenjangan | Perilaku yang harus dijamin |
| --- | --- | --- |
| T-01 | Profil perlu membatasi perubahan role dan enumerasi. | Pengguna tidak dapat mengubah role/status akses sendiri. Super Admin mengubah akun lain melalui RPC yang mencatat role/status lama/baru; role Super Admin aktif terakhir tidak dapat diturunkan/dinonaktifkan. Finance menerima nama penerima melalui laporan keuangan terbatas, tanpa membaca direktori profil. |
| T-02 | Relasi yang memakai nama kerja dapat rusak saat nama berubah. | Gunakan UUID profil untuk assignee dan anggota thread; nama hanya menjadi label tampilan. |
| T-03 | Payload chat dapat memalsukan identitas pengirim atau memilih thread yang tidak berhak diakses. | Backend menurunkan pengirim dari sesi Auth dan memvalidasi akses ke thread yang dituju. |
| T-04 | Nilai status/priority berasal dari klien. | Backend hanya menerima enum yang sah dan transisi yang diizinkan. |
| T-05 | Kapasitas atau presence dapat berubah saat job ditugaskan atau dialihkan. | Backend memeriksa kapasitas dan presence pada operasi penugasan/pengalihan dan mencegah dua permintaan bersamaan melampaui kapasitas, sesuai D-02 dan AC-14. |
| T-06 | Kebijakan Storage dapat terlalu luas atau memakai kunci yang melewati RLS. | Klien aplikasi memakai sesi pengguna; service key hanya di server tepercaya; pengguna tidak mengakses file di luar job yang berhak. |
| T-07 | Konfigurasi S3 backend dapat tidak cocok dengan versi bundle atau menyisakan objek lokal. | Uji upload, download, overwrite, dan delete melalui Supabase Storage lalu pastikan objek muncul/hilang di R2 dengan versi bundle yang dipin. |
| T-08 | Penghapusan objek dan metadata bisnis tidak berbagi transaksi. | Pembersihan bersifat idempoten; jika salah satu langkah gagal, retry menyelaraskan objek R2, `storage.objects`, `job_files.expired_at`, dan catatan retensi. |
| T-09 | Review dapat menyetujui berkas yang berbeda dari berkas yang diminta ACC. | Submission menyimpan relasi file yang tetap; ACC hanya menerima ID submission pending saat ini dan membekukan referensinya. |
| T-10 | Status, cancellation, atau assignment dapat berubah tanpa alasan/jejak. | Validasi wajibkan alasan untuk Revisi, cancel, dan reassign Dikerjakan/Revisi; simpan actor dan event dalam transaksi yang sama. Riwayat append-only. |
| T-11 | Fee, penerima rekap, atau hasil yang telah disetujui berubah setelah ACC. | Simpan `approved_fee`, `approved_for_profile_id`, dan `approved_submission_id` saat ACC dan tolak perubahan biasa pada ketiganya. |
| T-12 | Urgen, Terlambat, kapasitas, dan status terminal ditafsirkan berbeda antar klien. | Backend dan semua klien menggunakan definisi PRD: Urgen dari SLA antre; Terlambat dari deadline; kapasitas hanya status kerja yang ditugaskan; ACC/Dibatalkan terminal. |
| T-13 | Pendaftaran terbuka dapat disalahgunakan atau akun belum terverifikasi/disetujui mencoba memakai data. | Baru izinkan operasi setelah email diverifikasi dan pendaftaran disetujui; akun publik selalu Freelance. Operator bootstrap Super Admin pertama; setelah itu Super Admin mengelola role pengguna lain. RLS menerapkan cakupan empat role dan perlindungan abuse/rate limit Auth tetap aktif. |
| T-14 | Dua unggahan bersamaan dapat melewati kuota ukuran per job. | Buat reservation ukuran secara atomik sebelum transfer; jumlahkan file aktif dan reservation, tolak melebihi 10 GiB, dan lepaskan reservation gagal/kedaluwarsa. |
| T-15 | File besar atau metadata klien palsu dapat melewati batas. | Periksa ukuran aktual serta jenis konten di jalur server/storage, batasi file 1 GiB dan total 10 GiB untuk biner aktif/reservation per job, lalu catat `size_bytes` yang diverifikasi. |
| T-16 | Pengguna yang akses Threadline-nya dicabut masih memiliki sesi Auth. | `is_active=false` membuat helper identitas null dan menutup data/RPC melalui RLS; UI menampilkan akses nonaktif. Untuk offboarding penuh, operator juga menonaktifkan akun Auth dan mencabut sesi refresh; pertahankan profil, audit akses, dan riwayat job. |

## 7. Kontrak uji

Kriteria teknis utama berada di AC-01 sampai AC-36 pada [PRD](PRD-Threadline.md). Aplikasi dan migrasi lokal sudah tersedia di `threadline/`, tetapi kriteria penerimaan belum diverifikasi melalui deployment dan alur lintas perangkat.
